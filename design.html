Airlock Scratchpad — Design & Security

This document describes the app as it is. It is not a changelog and not a record of how the app came to be; it states what Airlock Scratchpad does with your credentials, what it defends against, and — at the same length — what it does not.

The source is closed. That is exactly why this exists: "trust me" is not an argument anyone should accept about a tool that holds credentials, so the design is written down in enough detail to be argued with.

What it is

A local, encrypted scratchpad for the short-lived credentials a developer handles during a working day: API keys, access tokens, database passwords, SSH keys, certificates.

The problem it addresses is not that vaults are bad. It is that getting a credential out of a proper vault takes a minute, and you may need it eight times in an hour. So the value gets pasted somewhere convenient — a scratch file, a note, a message to yourself — and that copy is plaintext, indexed by Spotlight, possibly synced, and never cleaned up. A key pasted into a scratch file months ago is still sitting there.

Airlock is somewhere to put that copy instead: encrypted, behind a second authentication, and deleted on a deadline.

What it is not

Not a password manager. Anything that must outlive today's work belongs in a real vault — 1Password, Bitwarden, HashiCorp Vault, AWS Secrets Manager. Airlock will not stop you keeping something indefinitely, but nothing about it is built for that, and the app says so on its first Help screen.

Not a config store. It lists plain configuration when importing a .env so nothing is hidden from you, but it does not tick it for import and does not treat it as a credential.

Not a sync service. There is no account, no server, and no network code.

Not a team tool. Shared credentials need access control and an audit trail. Building half of that would be worse than not building it, because it invites a use it cannot safely support.

Threat model

What it is built to defend against

  • A lost or stolen Mac. The vault is encrypted at rest and the key is held in hardware that cannot be read out.
  • Casual local access. Someone at your unlocked desk sees item names, not secrets — revealing a value requires authenticating again.
  • Plaintext sprawl. Nothing is written to disk in the clear: no cache, no temporary file, no plaintext index. The secret that would otherwise sit in a scratch file has a home that forgets it.
  • Accidental disclosure when sharing. Logs and config dumps can be scrubbed of credentials before they are pasted into a ticket or a chat.
  • Screen recording and screen sharing. The window is excluded from capture while anything sensitive is on screen.
  • Indefinite retention. Expiry is the default rather than an option.

What it is explicitly not built to defend against

  • Malware running as you. Code with your privileges on your machine, while the vault is unlocked, sees what you see. No app-level design defeats that.
  • A compromised operating system. Everything here rests on macOS and the Secure Enclave behaving as documented.
  • A determined attacker with your unlocked Mac and your finger. The reveal gate raises the cost of casual access; it is not a defence against coercion.
  • Anything you take out. A key copied to ~/.ssh, pasted into a file, or sent to a colleague has left. The app protects the copy it holds.

No network, no dependencies

There is no networking code in the app. Not disabled, not optional — absent. No URLSession, no sockets, no web views, and the sandbox entitlement for network access is not requested, so macOS would refuse the attempt even if some code tried.

That single fact is what makes most other claims checkable: nothing Airlock holds can reach anywhere, because the app has no means of sending it.

There are no third-party libraries and no package dependencies. Every cryptographic primitive is Apple's own — CryptoKit and CommonCrypto. This is a deliberate limit, not a preference: a dependency is code you did not write, running with your secrets in reach, and each one makes you part of a supply chain you did not choose.

It also has a cost, stated plainly below rather than glossed over.

What is stored, and where

One encrypted file, inside the app's own sandbox container on your Mac.

Everything is inside that single encrypted payload — items, their names, their types, their deadlines, and the projects you filed them under. There is no index, no metadata table, and no list of names outside the encryption. Somebody holding the file learns nothing from it but its approximate size.

Project names are part of the encrypted payload for the same reason: a project called acme-acquisition tells a reader a great deal before they have seen a single secret.

Padding. The payload is padded to 4 KB blocks before encryption, so the file's size indicates roughly how much you keep rather than how many items you have.

Encryption

AES-256-GCM, via CryptoKit, over the whole payload.

GCM is an authenticated cipher, and that matters more here than the key size: a file that has been modified — even by a single bit — fails to open rather than decrypting into something plausible. Corruption and tampering are the same event, and both are refused rather than guessed at.

The vault key, and the three ways in

A random 256-bit vault key encrypts the payload. That key is never written down in any form. What the file holds is the key wrapped — itself encrypted — under each unlock method you have enrolled. Each wrap is useless without the thing that opens it.

Touch ID (or your login password)

A P-256 key is generated inside the Secure Enclave and never leaves it. It cannot be exported, copied, or moved to another Mac, because the hardware provides no operation that would emit it. The vault key is wrapped to it by key agreement, with the wrapping key derived through HKDF-SHA256.

The Enclave releases its half only on user presence, which is what makes the Touch ID prompt a gate rather than a question.

On a Mac without Touch ID this uses your login password instead, through the same system mechanism. Nothing about the design requires biometrics.

The backup password

Optional. Run through PBKDF2-HMAC-SHA512 at 210,000 iterations to derive a key-encryption key. The iteration count is stored alongside the wrap, so it can be raised in a later version without stranding vaults created under the old one.

A password must be at least 15 characters and is checked against a list of known-compromised passwords. There are no composition rules — length is what matters, and a memorable passphrase of several words beats a short complicated one.

The recovery code

Optional, and the one to set up. 160 bits from the system's random number generator, displayed once, printable, derived with HKDF-SHA256.

Why it skips the slow derivation. Iteration counts exist to make guessing expensive, and guessing is only a threat when the secret is guessable. A password you invented has perhaps 40 bits of real entropy, which is why it needs 210,000 rounds standing in front of it. A recovery code has 160 bits and nothing to guess — there is no shortcut for an attacker to be slowed down on. A slow KDF there would cost you time and buy nothing.

The alphabet excludes the characters that are misread off paper, and unlocking accepts them interchangeably, because a recovery code that fails because someone wrote a capital I is not a recovery code.

All three open the same key

Which is why adding or removing an unlock method never re-encrypts your data and never puts it at risk. They differ in how they are protected, not in what they open.

There is no reset. No server, no account, no recovery link. With Touch ID alone, losing the Mac loses the vault — the Enclave key is bound to that machine. That is the design working as intended, and it is the reason the recovery code exists.

One honest caveat

CryptoKit ships no memory-hard key-derivation function — no Argon2id, no scrypt — and the no-third-party-crypto rule is not negotiable for a tool like this. PBKDF2-HMAC-SHA512 at 210,000 iterations is therefore the strongest option genuinely available here, not the strongest option that exists.

That trade is deliberate. It is also why the recovery code is offered: it does not depend on a human-chosen secret at all.

While the app is running

  • Decrypted items exist only in memory, and only while unlocked.
  • Locking discards the key and every decrypted value. It happens on inactivity, on demand, and when you close the window.
  • Revealing asks again. Being inside an unlocked vault is not consent to see a secret. After a successful reveal there is a grace period so you are not prompted repeatedly — but the gesture remains on every secret, so clicking through your vault does not expose everything you clicked.
  • Copying counts as access and is gated the same way. You do not have to look at a secret to use it.
  • The window is excluded from screen capture and screen sharing while locked and while anything is revealed. Recording software gets a blank window.
  • Copied secrets are marked concealed on the clipboard, and the clipboard is cleared automatically. The concealed flag is a convention that clipboard-history tools honour voluntarily — macOS does not enforce it — so the auto-clear is the part that does not depend on anyone else's cooperation.

Expiry

There is exactly one expiry rule, and no feature is allowed its own.

Every item has a deadline — three days by default, adjustable globally and per item. When it passes, the item goes: to the Recycle Bin if you have enabled one, permanently if you have not.

  • Editing does not reset the clock. Changing a secret's name or fields is not evidence you still need it. Neither is moving it between projects. Only changing the expiry changes the expiry.
  • A credential's own lifetime is tracked separately. A certificate's notAfter, a JWT's exp, a session token's expiry are read and kept apart from Airlock's deadline, so the app can say "this token is dead" as distinct from "this copy is being tidied away".
  • A credential that outlives its copy by a wide margin is flagged, not silently truncated. A 90-day certificate against a 3-day default is a decision for you to make.

Where a feature seems to want its own expiry behaviour, the app surfaces the consequence instead. Importing a rotated value shows how long the item it replaces has left, rather than quietly restarting its clock.

Reference documents kept in the app are the one thing that does not expire — they contain no credentials, and a reference page that deleted itself would be worse than useless.

Scrubbing before you share

Scrub for Sharing takes text on the clipboard — a log, a config dump, a stack trace — and replaces credentials in it with placeholders.

It runs in two passes.

1. Every secret your vault holds that appears in the text is removed by exact match. Nothing has to be recognised, so an in-house token format that no heuristic could guess is still caught — provided you have stored it. Where the item has an export variable, the placeholder names it, so the text still says what was there without saying what it was. 2. Shape rules then run for anything the vault has never seen: recognisable vendor tokens, JSON web tokens, passwords inside connection strings, named assignments that look like credentials.

The second pass is deliberately cautious. It removes only what it is confident about, because a scrubber that mangles ordinary log lines is one you would turn off — which means a credential you have never stored, in a format it does not recognise, can still get through.

You are shown exactly what was found and what the result looks like before anything is copied back. Read it before you send it.

What this does not protect you from

A security page that lists only strengths is marketing. These are real.

  • Malware running as you, while the vault is unlocked. It sees what you see.
  • Memory. Key material and derivation buffers are wiped where the language allows it, but Swift's String can move and copy itself, so a revealed secret cannot be guaranteed gone from memory until the process exits.
  • Anything you export. A private key copied to ~/.ssh is no longer protected by anything here. Generated SSH keys carry no passphrase — the app cannot add one, because OpenSSH protects private keys with a bcrypt KDF that macOS does not provide — and the app says so on the item rather than leaving you to discover it.
  • A lost Mac with no recovery code. Unrecoverable by design.
  • A shoulder, a camera, or a coerced finger. The reveal gate raises the cost of casual access. It is not a defence against a person standing next to you.

Checking the claims yourself

The source is closed, so here is what you can verify without it.

That it requests no network access, and exactly three entitlements:

codesign -d --entitlements - /Applications/Airlock.app

You should see app-sandbox, files.user-selected.read-write and print, and nothing granting network, camera, microphone, contacts, or location. A build installed from the App Store carries exactly those. (A developer build also carries get-task-allow, which is what makes it debuggable and is not present in a released one.)

That it links no third-party frameworks:

otool -L /Applications/Airlock.app/Contents/MacOS/Airlock

Every entry should be inside /System/Library or /usr/lib.

That it talks to nothing. Watch it with Little Snitch, LuLu, or any outbound firewall, for as long as you like. There is nothing to see, which is the point.

That the vault is opaque. The file lives in the app's container under ~/Library/Containers/com.rabcon.AirlockScratchpad/. Open it in any editor: it is ciphertext, padded, with no readable names.

Non-goals, and why

  • Sync. Would need a server or a cloud account, and a secret you need on two machines belongs somewhere with proper access control.
  • Sharing. Needs access control and an audit trail. Half of that is worse than none.
  • TOTP codes, autofill, browser integration. Each is individually reasonable and collectively they turn this into a worse password manager.
  • Third-party cryptography, including for bcrypt-protected SSH keys. The gap is made loud instead: the app tells you the key is unprotected and gives you the exact command to fix it after export.
  • A backup or export of the vault. Deliberate. These credentials should also exist somewhere that is designed to keep them; an export would encourage treating this as the place they live.
