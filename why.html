An airlock is not a room you live in. It is the chamber between two pressures, where you pass through safely — and it is empty again afterwards.

The problem

Secrets leak sideways, not through the front door

Nobody decides to keep a production database password in a text file. It happens anyway, because the alternative is unlocking a vault, navigating to an entry, copying a field, and doing that again four minutes later when the shell scrolls away.

So the key lands somewhere convenient. A scratch file. An untitled tab. A note. A message to yourself. The clipboard, for the rest of the day.

Those copies are the actual problem. They are in plaintext. They are indexed by Spotlight. They sync to other machines. Backups pick them up. And crucially, nothing ever cleans them up — a key pasted into a scratch file in March is still sitting there in September, long after it stopped being needed and long before anyone thinks to rotate it.

The vault did its job. The leak happened downstream of it, in the gap between where secrets are stored and where work actually happens.

Positioning

This is not a password manager

We should be blunt about this, because getting it wrong is the one way Airlock Scratchpad could make things worse rather than better.

Anything that has to outlive the work you are doing today belongs in a real vault. Airlock has no sharing, no access control, no audit trail, no rotation and no recovery. It is not a system of record and it will never become one.

Tool Holds For how long
Secrets managerVault, AWS, GCP What production reads at runtime Indefinitely, with rotation
Password manager1Password, Bitwarden Your credentials and your team's Indefinitely, shared and audited
Airlock The working copy on your desk today Three days, then gone
A scratch fileWhat this replaces Whatever you pasted, in the clear Forever, unnoticed

Airlock competes with the fourth row. It has no opinion about the first two, except that you should be using them.

Design rules

Three commitments the app actually keeps

01

Everything expires

Three days unless you say otherwise. There is exactly one expiry rule in the app — nothing sets its own deadline behind your back, and editing a secret does not buy it more time. Editing is not evidence you still need something.

02

Nothing is stored in the clear

Not on disk, not in a temp file, not in a database. Items exist decrypted in memory only, and only while the vault is unlocked. Locking drops every value.

03

Being in the app is not permission

Unlocking shows you what you have — names, types, deadlines. Seeing or copying an actual value asks you to authenticate again, every time.

Expiry

A credential and a copy of it die on different days

This distinction turned out to matter more than anything else in the design. A certificate is valid for ninety days. Your copy of it should not be.

So Airlock keeps two clocks and never conflates them. When a credential states its own lifetime — a certificate's notAfter, a JWT's exp, an AWS session token's expiry — that gets read and kept separately.

Clock one · the issuer's Validity

When the credential stops working. Not your decision, and not something Airlock can change.

"This token is dead."
Clock two · yours Hygiene

When this copy gets tidied away. Entirely your decision, adjustable globally or per item.

"This copy is being cleaned up."
Mismatches are flagged, never silently resolved

A ninety-day certificate against a three-day default is not a bug to fix quietly — it is a decision you should get to make. Airlock surfaces it and waits. Extend the copy, or move the credential somewhere built to hold it for ninety days.

In practice

The whole point is that it is faster than the bad habit

A tool that protects secrets by being tedious does not protect anything, because people route around it. Airlock has to beat a scratch file on convenience or it fails on its own terms.

  • Copy, then ⌘⇧V. Airlock recognises what you pasted — a ghp_ GitHub token, an sk_live_ Stripe key, a PEM block, a connection URI — and opens the matching template with the fields already filled in. One keystroke, no form.
  • Drop a .env file. It reads the whole thing, shows you which entries are secrets and which are plain config, and tells you what you already hold. Re-import after a rotation and it reports "7 unchanged, 2 rotated, 1 new" instead of duplicating everything.
  • Copy without looking. You rarely need to see a secret, only to paste it. Copy sits next to Reveal and never requires unmasking anything.
  • Scrub before sharing. About to paste a log into a ticket? One button replaces the credentials in it with placeholders, and shows you exactly what it found before anything leaves.
Non-goals

What we deliberately did not build

Each of these was considered and rejected. The absences are the design.

Sync and sharing A shared secret needs access control and an audit trail. Building half of that is worse than building none: it invites the use it cannot safely support.
A recovery path No server, no account, no reset link. The Secure Enclave key is bound to one Mac. That is the security model working as intended, and it is why the password backup exists.
Third-party packages A security app's supply chain is part of its threat model. Apple frameworks only, zero third-party crypto — an unaudited AES implementation would be the highest-risk dependency this app could take.
Browser autofill A different problem, already solved well by password managers, and one that would mean injecting credentials into pages Airlock cannot vouch for.
A default that never expires Permanence is available per item, but it is opt-in and gated. The moment "keep forever" becomes the easy path, this stops being an airlock and starts being another place secrets accumulate.
How it is built

The specifics, since a security claim is worthless without them

EncryptionAES-256-GCM · CryptoKit
Key protectionSecure Enclave P-256, user presence
Key wrappingECDH + HKDF-SHA256
Password KDFPBKDF2-HMAC-SHA512 · 210,000 rounds
Password floor15 characters, breach-screened
Recovery code160 bits · HKDF-SHA256 · shown once, printable
Payload padding4 KB blocks — file size leaks no item count
SandboxEnabled · app's own container
Screen captureWindow excluded while revealed
DependenciesNone

One honest caveat on that list. CryptoKit ships no memory-hard key-derivation function — no Argon2id, no scrypt — and the no-third-party-crypto rule is not negotiable for a security tool. PBKDF2 via CommonCrypto at 210,000 iterations is therefore the strongest option genuinely available, not the strongest option that exists. That trade was made deliberately, and it is written down rather than glossed over.

If a secret needs to outlive the work, it belongs somewhere else — and Airlock will tell you so.

Everything here follows from one idea: the dangerous copy of a secret is not the one in the vault. It is the one on your desk that nobody is keeping track of. Give that copy a proper home and an expiry date, and the habit stops being a liability.
